# FSR 4.1.2 Lite Lossy и опциональные улучшения

Новые режимы реализованы независимо для Metal. Это не запуск Windows DLL и
не обещание побитового совпадения с её lossy-выходом. Обычные Lite и Exact
остаются по умолчанию без новых правил истории.

## Режимы

| Профиль | Что делает |
| --- | --- |
| `int8-lite` | Оригинальная AMD Lite-сеть на каждом кадре, прежний default |
| `int8-lite-lossy` | Переобученные Lite-веса и повторное использование параметров через кадр |
| `int8-lite-lossy-tiled` | Эксперимент: половина квадратных блоков обновляется каждый кадр |
| `int8-lite-lossy-original` | Opt-in: оригинальные PRE/BORDER/POST релиза плюс точные native INT8 нейростадии |

В панели v3.0 доступен **FSR 4.1.2 Lite Lossy** при наличии правильных
данных и квитанции импорта. **Lite Lossy Tiled** убран из выбора в панели;
он остаётся экспериментальным CLI-профилем. CLI-установщик принимает оба
имени. Старые номера сохранены: 7 для whole, 8 для tiled. Сохранённый выбор
не подменяется, если данные отсутствуют или режим больше не предлагается.
Свежие замеры с прогревом: [FSR_V3_BENCHMARKS.md](FSR_V3_BENCHMARKS.md).

```sh
make lite-lossy-weights
make
tools/bin/fsr4mac testcases/tc_game_balanced out/lite-lossy --fsr-version 4.1.2 --profile int8-lite-lossy
```

Для CrossOver:

```sh
python3 tools/crossover/crossover_fsr4.py install --panel --fsr-version 4.1.2 --profile int8-lite-lossy
```

Закрой игру и бутылку перед установкой. Изменения в уже установленные бутылки
не применяются автоматически при редактировании исходников.

## Откуда веса и что проверяется

### Оригинальный граф (`int8-lite-lossy-original`)

Этот режим не приближает временную логику, а исполняет переведённые
оригинальные шейдеры PRE, P1-border, BORDER и POST из пиннутого релиза
`dll-2026-11-01` (DLL `d9b0a1f5...`). Нейростадии CNB, DS, FNB и CT
считаются точными native INT8 kernels (MPP, SIMD или scalar). Решение о
пропуске сети принимает оригинальный PRE через GPU-маркер; native kernels его
соблюдают. Геометрия чтения и записи соответствует `docs/FSR412_ORIGINAL_GEOMETRY.md`.

Сборка бандла (GPL-данные только в `build/`, DLL не исполняется):

```sh
python3 tools/fsr412/upstream_oracle.py DLL --reference AMD_4.1.1_DLL   # один раз, статический импорт
export FSR412_DXIL_SPIRV=/path/to/dxil-spirv                           # существующий конвертер
tools/bin/fsr4mac testcases/tc_game_balanced out/original --fsr-version 4.1.2 --profile int8-lite-lossy-original
```

В live-хуке: профиль Lite Lossy (ID 7) и `FSR4_LITE_LOSSY_ORIGINAL=1`.
Размер вывода должен делиться на 4. Неподходящие режимы (tiles, POST tiling,
hair fix, reference backend) отклоняются.

Проверка (`make test-fsr412-original`): production `Runtime::encode` против
oracle на одинаковых входах, побитово output, history, recurrent, reprojected
и весь логический scratch на каждом кадре. Прошло для MPP, SIMD и scalar,
classic Metal и Metal 4, `640x384`, `644x388`, `1920x1080` и `3840x2160`,
включая кадры с повторным использованием сети. Это совпадение с переводом
оригинала на Metal, **не** наблюдение Windows-исполнения.

Найдено при проверке: Metal `-O3` неверно компилирует оригинальный P2, поэтому
oracle собирает P2/P3 с `-O0`; классификатор auto-exposure был инвертирован
(исправлено, ревизия бандла 2).

Скорость (M5, GPU-время всего кадра, чередующиеся режимы, по 2 запуска, синтетический
вход `fsr412_modes_ab --original --auto-exposure`):

| Вывод | `int8-lite` | `int8-lite-lossy` медиана | `original` полный кадр | `original` повтор |
| --- | --- | --- | --- | --- |
| 2560x1440 | 4,44 мс | 3,37-3,42 мс | 7,21 мс (было 16,6) | 8,38 мс |
| 3840x2160 | 9,87 мс | 7,53 мс | 14,94 мс (было 36,0) | 17,55 мс |

На кадрах с полным пересчётом сети POST читает CNB, заранее посчитанный
точным native kernel, вместо скалярной эмуляции packed INT8 dot4 (POST 4K: 38,4 -> 5,8 мс).
На кадрах с повторным использованием идёт неизменённый оригинальный POST.
Причина (`docs/FSR412_ORIGINAL_POST_CNB.md`): при промахах изменяемого кэша оригинал
на Metal даёт разный результат при разном порядке групп (до ~2 КБ output и ~39 КБ recurrent
на стресс-тесте 4K), поэтому единственного «точного» ответа там нет.

Ускорение POST сейчас закреплено за одним проверенным вариантом: класс 2160
(вывод больше 1920x1080), normal, linear, auto-exposure включено. Остальные
варианты, в том числе всё до 1080p и без auto-exposure, работают через оригинальный
POST: так же точно, но примерно вдвое медленнее `int8-lite-lossy` (1080p: 5,4-6,5 мс против
2,6-2,75 мс). Режим не включён по умолчанию.

### Веса

`tools/fsr412/fetch_lossy_weights.py` скачивает закреплённый RX 7000 архив
`dll-2026-11-01`, проверяет SHA-256 архива и DLL, статически читает DXIL через
локальный DXC и пишет данные в `build/fsr412_lossy/`. DLL не исполняется.

- Архив SHA-256: `743adcd599dee3cbf6035ed08ceeced987b75178f74a22b945a421d030d8d34e`.
- DLL SHA-256: `d9b0a1f5781c2d633a327272f6f1c8607057df7cafd0233cf38c7395c8f7dbc5`.
- Итоговый initializer, 27 392 байта: `c77c2d1a4d119ed76d94b8c23335490cc38280db3346c72396a1e1acb0523cfc`.

Декодер проверен на точном соседнем DLL: восстановлены все таблицы AMD,
включая POST-хвост. Обученные normal-варианты 1080/2160 совпадают между собой;
Ultra Performance и класс 4320 используют AMD-веса, как исходный проект.
Повторное использование на классе 4320 отключено, даже если текущий viewport
меньше 4K. Отчёт кадра содержит `upstream_retrained_weights`.

Квитанция сохраняет хеши контейнеров, смещения, округления и условные различия.
Четыре отдельных набора POST CT-смещений применяются по чётности пикселя,
а не усредняются. Их матрица также закреплена хешем.

**Оставшееся отличие:** upstream POST сохраняет старые AMD-смещения первого
3x3 tap на части границ. Native-адаптация использует основной обученный bias.
Это отмечено в квитанции; полного совпадения с DLL на границах не заявляется.

Обычный whole-режим в панели остаётся опциональным и меняет картинку.

Данные upstream отмечены GPL-2.0-or-later и не включаются в MIT-исходники или
обычный release ZIP. Не переносите GPL-исходники/данные в пакет без отдельной
проверки лицензии. `make lite-lossy-weights` является явной внешней загрузкой.

## Безопасное повторное использование

Сохраняются восемь целочисленных POST-параметров **до** sigmoid и масштабирования.
Их границы превышают int16, поэтому используется точный int32, не усечение.

- Whole-режим пишет кеш только на полном кадре и читает только на повторном.
  Два повторных кадра подряд запрещены.
- Tiled использует разные previous/current буферы. Каждый кадр обновляет
  весь кеш: новые параметры либо перенос предыдущих по движению.
- Сбросы, смена варианта/размера и большие изменения pre-exposure требуют
  полного расчёта. Все ресурсы удерживаются до завершения GPU.
- Проверки истории используют движение 2x2, текущий диапазон цветов и
  ограниченную проверку поддержанных ярких искр.

Цена памяти: один raw-кеш занимает 66,4 МБ при 1080p и 265,4 МБ при 4K.
Tiled требует два таких кеша. Motion plane добавляет 8,3 / 33,2 МБ.
Это **не** бюджет памяти исходной Radeon-реализации и не учитывает обычные
scratch/history/цветовые текстуры. На малом объёме RAM tiled нежелателен.

## Опциональный кэш Lite POST

```sh
tools/bin/fsr4mac CASE OUT --fsr-version 4.1.2 --profile int8-lite --post-tiling 1
```

`FSR4_POST_TILING=1` включает его в live. Требуется `optimize=1`.
Группа GPU совместно читает небольшой прямоугольник цветов, максимум
24x24 float4 (9216 байт). Геометрия dispatch и формулы модели сохранены.
Неподходящий масштаб или выход за область кеша использует прямое чтение.

На M5/Xcode 27 обнаружена и исправлена проблема fast-math: inline-чтение из
threadgroup меняло единицы half-значений истории, которые усиливались на
следующем кадре. `noinline`-граница чтения сохранила прежнюю арифметику.
Побитово проверены output и все состояния двух записанных кадров, в том числе
отдельный RGBA32F POST replay. На остальных GPU/toolchain это нужно повторить.

## Обновление половины блоков

```sh
tools/bin/fsr4mac CASE OUT --fsr-version 4.1.2 --profile int8-lite-lossy-tiled --neural-tile-size 512
```

Допустимы 128, 256, 512, 1024 и 2048; `0` возвращает whole-режим.
Live override: `FSR4_NEURAL_TILE_SIZE=512`. Промежуточные нейросетевые проходы
считают дополнительную границу 32 выходных пикселя. Группы пропускаются
только целиком, до любых барьеров. Внешние два пикселя всегда обновляются.

Это эксперимент, а не гарантированное улучшение плавности. Картинка отличается;
границы блоков и движущиеся объекты требуют проверки в конкретной игре.

## Улучшенная история обычного Lossy

Для полноразмерной сети с внутренним именем `lossy2`:

```sh
tools/bin/fsr4mac CASE OUT --fsr-version 4.1.1 --profile lossy2 --temporal-quality 1
```

`FSR4_TEMPORAL_QUALITY=1` включает fine motion 2x2, двухкадровые знаки изменений,
плавные изменения света и ограниченный spark-test. `0` сохраняет старый путь.
Режим `2` - отдельный fast-notes эксперимент: использует уже вычисленный
текущий цвет вместо дополнительных bilinear-сэмплов, с Wave32 gather и
консервативным fallback. Эти флаги не применяются к FSR 4.1.2 Lite.

На шести синтетических SDR-сценах режим 1 относительно старого lossy2:

| Сцена | PSNR до | После |
| --- | ---: | ---: |
| Провода при панораме | 25,74 | 26,18 |
| Тёмные частицы без движения | 61,73 | 62,63 |
| Движущийся объект | 44,80 | 45,20 |
| Тонкая полоса на движущемся фоне | 33,60 | 33,65 |
| Провода в покое | 27,34 | 27,31 |

Зерно почти не меняется, временная ошибка в некоторых спокойных сценах немного
хуже. Это не оценка всех игр/HDR. Консервативный режим заметно дороже.

## Производительность и проверки

Первый M5 interleaved synthetic A/B, 864x560 -> 1712x1112, 256 кадров на режим,
RCAS off: среднее Lite 2,485 мс, Lite Lossy 2,309 мс, POST tiles 2,536 мс,
Lossy tiled 2,891 мс. Legacy lossy2 2,671 мс, conservative quality 3,839 мс.

Повтор записанного `tc_game_balanced`, шесть чередующихся запусков по 70 кадров:
медиана среднего Lite 3,433 мс, Lite Lossy 3,241 мс, POST tiles 3,294 мс,
Lossy tiled 3,791 мс. Разброс большой: прирост не гарантирован и это не FPS игры.
Поэтому default не изменён, новые оптимизации включаются явно.

Повтор synthetic A/B с fast notes: legacy lossy2 2,764 мс, conservative
quality 3,867 мс, fast quality 3,691 мс. Fast notes дешевле conservative,
но всё ещё около 34% дороже исходного режима. В тех же SDR-сценах fast:
провода при панораме 26,18 дБ, тёмные частицы 62,27 дБ, движущийся объект
45,13 дБ, провода в покое 27,33 дБ.
Полная сводка: [fsr412-new-modes-m5-2026-11-01.json](reports/fsr412-new-modes-m5-2026-11-01.json).

```sh
make test
make test-fsr412-lossy
make test-fsr412-post-tiles
make bench-fsr412-modes
python3 tools/bench/benchmark_fsr412_modes.py testcases/tc_game_balanced
```

Whole/tiled проверены на classic Metal и Metal 4: native/scalar/SIMD кадры и
состояния совпадают, cache ownership и сбросы соблюдаются. Ultra Performance
также проверен на classic. Старый Exact сравнен с бинарником HEAD: два
записанных кадра и все состояния остались побитово одинаковыми.

Полные локальные отчёты: `build/lite-lossy-review/`. Физические M1-M4,
долгие игровые сессии и качество HDR не проверены этим набором.
