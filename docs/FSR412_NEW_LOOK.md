# Experimental new-look для FSR 4.1.2 Lite Lossy

Опциональная обработка истории по формулам cyboman из
[issue #20](https://github.com/UzenUPoZiTiV4ik/fsr4-native-macos/issues/20#issuecomment-6839502725).
Это другой вид картинки на той же нейросети, не новые веса и не ускорение FSR.
Реализация написана независимо по объяснению автора; GPL-генератор не импортирован.

## Как включить

1. Подготовьте опциональные веса обычным `make lite-lossy-weights`.
2. В панели выберите **FSR 4.1.2 Lite Lossy**.
3. Включите оранжевый флажок **Experimental new-look**.

Флажок по умолчанию выключен и недоступен для остальных моделей. Выбор
запоминается при переходе к другой модели, но применяется только к Lite Lossy.
Резкость, RCAS, Pixelization fix и выбор MetalFX/ANR сохраняются независимо.
Настройка `new_look=0|1` хранится в `dist/crossover/panel.conf`.

Переключение перечитывается в игре, сбрасывает историю и переводит следующий
кадр на полный расчёт. При первом включении возможна подготовка шейдеров.
После обновления самого хука игру нужно перезапустить; редактирование
исходников не обновляет установленные бутылки автоматически.

CLI для проверки записанных кадров:

```sh
tools/bin/fsr4mac CASE OUT --fsr-version 4.1.2 --profile int8-lite-lossy --new-look
```

## Какие правила добавлены

- Проверки изменения цвета используют диапазон девяти новых сэмплов с точными
  порогами из объяснения автора, а spark-test считается отдельно по каналам.
- Яркий компактный объект, которого ещё не было в истории, обновляется раньше.
  Четыре пробы на расстоянии 8 render-пикселей отличают его от широкой полосы
  на повторяющихся узорах, чтобы не усилить муар.
- Ограничение пересвеченных одиночных точек сохраняет линии: пара соседей
  хотя бы в половину яркости центра не считается одиночной искрой.
- На пропущенном кадре для ячеек не в покое тёмные и белые точки ограничиваются
  при перепаде глубины **или** если у блока нет валидной записи глубины.
  Валидная ровная глубина сама по себе не открывает это условие. Проверки
  среднего цвета уменьшают риск удержания старого цвета крупного объекта.
- Двухкадровые знаки изменений и медленное изменение зелёного канала сохраняются
  в свободной альфе истории, включая полные кадры. Новых буферов для знаков нет.
- На неподвижных ячейках рядом с другим движением третий канал памяти получает
  минимум 0.45. Малые изменения удерживаются dead-band правилом, но продолжающийся
  медленный fade из него освобождается.
- В Ultra Performance соблюдается дополнительное условие jitter Y из оригинального
  PRE. Наши защиты от двух повторных кадров подряд и скачков pre-exposure остаются.

Все цветовые пороги применяются в **логарифмическом рабочем пространстве Lite**,
не к обычному RGB экрана. Граф, веса, целочисленные ядра и CT-параметры прежние.

## Ограничения

- Только whole-frame Lite Lossy, линейный вход и вывод до 4K. Tiled,
  `int8-lite-lossy-original` и nonlinear/sRGB/PQ варианты явно отклоняются.
- Это не побитовое совпадение с DLL cyboman. У нас остаётся приближённая
  проверка владельца движения/глубины, а не оригинальный scatter предыдущих
  владельцев. Чтения истории на границе также консервативно ограничены текстурой.
- Возможны дополнительная мягкость, шлейфы или GPU-нагрузка. Игры и HDR
  этими тестами не проверялись. При ухудшении выключите флажок.
- Обычный Lite Lossy с выключенным флажком, Lite, Exact, Netal и ANR не меняются.

## Опубликованная проверка v3.2 на Apple M5

- CPU/source проверки: выключенный transform побайтово совпадает с v3.1
  для линейных PRE/POST, включая подготовленный цвет.
- 1002 случая скалярных цветовых правил проверены на настоящих Metal 3 и
  Metal 4: результат между API совпадает побайтово, с CPU в пределах `3e-5`.
  Защитные байты выходного буфера сохранены.
- Полный Lite Lossy: MPP/scalar/SIMD совпадают по output/history/recurrent,
  включая переключение new-look, сбросы, изменение экспозиции и UP.
- AppKit проверяет нажатие флажка, сохранение прочих настроек и геометрию панели.

Пять аналитических SDR-сцен, 192x108 -> 384x216, 32 кадра, из них первые
8 исключены. Эталон - интеграция 8x8 сэмплов; это не вывод AMD или Windows DLL.
PSNR выше означает меньшую среднеквадратичную ошибку:

| Сцена | Прежний Lite Lossy | new-look |
| --- | ---: | ---: |
| Провода при панораме | 25.86 dB | 25.87 dB |
| Яркие частицы | 57.13 dB | 57.36 dB |
| Тёмные частицы | 61.23 dB | 63.04 dB |
| Движущийся объект | 44.59 dB | **43.33 dB, хуже** |
| Зерно | 42.72 dB | 42.75 dB |

У движущегося объекта также на 9.9% выросла временная ошибка. Это причина
не включать new-look по умолчанию, а не обещание улучшения всех игр.

Короткий interleaved timing при 1280x720 -> 1920x1080: медиана GPU-времени
6.29 ms у Lite Lossy и 6.56 ms у new-look, примерно +4.3%. 128 измеренных кадров
на режим, 16 warmup-кадров, чередующийся порядок. Это короткая диагностика,
не длительный тепловой тест, не игровые FPS и не сравнение с таблицами v3.0.
[Числа и условия](reports/fsr412-new-look-m5.json).

```sh
make test
make test-fsr4-panel-ui
make test-fsr412-new-look
```

## Проверка регрессии на движущемся объекте

В опубликованной сцене `moving_object` фон уже имеет глубину 0.7, а объект
0.2. Поэтому [гипотеза из issue #20](https://github.com/UzenUPoZiTiV4ik/fsr4-native-macos/issues/20#issuecomment-6893023501)
об отсутствии глубины не объясняет её напрямую: ограничения всё ещё могут
срабатывать вдоль контура. Проверка ниже меняет только два правила (floor
2.10 и ceiling 2.11) в POST, не меняя веса, остальные правила или настройки игры.

На Mac с Apple Silicon и Metal Toolchain, после
[импорта модели и шейдеров](../README.md#quick-start-from-source-play-a-game-in-crossover)
и установки NumPy, из корня репозитория:

```sh
make lite-lossy-weights
python3 tools/diagnostics/fsr412_new_look_ablation.py build/new-look-depth-step
# Контроль: те же цвет, векторы движения и эталон; глубина всюду 0.7.
python3 tools/diagnostics/fsr412_new_look_ablation.py build/new-look-depth-flat --depth flat
```

Результат на Apple M5, Metal INT8 SIMD: оценены 24 из 32 кадров после прогрева
истории, с одинаковым расписанием полного расчёта во всех режимах.

| Глубина | Режим | PSNR, дБ | PSNR пропущенных, дБ | Временная ошибка |
| --- | --- | ---: | ---: | ---: |
| С перепадом | Lite Lossy | 44.59 | 43.68 | 0.0005224 |
| С перепадом | new-look | 43.33 | 41.62 | 0.0005743 |
| С перепадом | new-look без floor/ceiling | 44.52 | 43.40 | 0.0004563 |
| Ровная | Lite Lossy | 41.37 | 40.04 | 0.0007036 |
| Ровная | new-look | 41.96 | 40.71 | 0.0005948 |
| Ровная | new-look без floor/ceiling | 41.96 | 40.71 | 0.0005948 |

На сцене с перепадом отключение пары вернуло около 95% потери PSNR и снизило
временную ошибку на 20.5% относительно полного new-look. При ровной
**валидной** глубине (не при её отсутствии) измеренные метрики не изменились.
Это показывает, что пара правил объясняет большую часть регрессии на этой
сцене; вклад каждого правила по отдельности не измерен. Поведение в игре
не изменено: эта проверка не оценивает пользу ограничений на листве.

## Внешние эталоны cyboman

[reference-scenes-1](https://github.com/zgauthier2000/fsr4-shader-performance-overrides/releases/tag/reference-scenes-1)
содержит три синтетические сцены: движущиеся объекты (`ref1080_moving`),
тонкие провода при панораме и листву. В каждой — 12 кадров от сброса,
1130×636 → 1920×1080 (Balanced), входы и эталон, а также вывод AMD FSR 4.1.1,
AMD FSR 4.1.2 Lite из тестового стенда cyboman и выпущенного `4.1.2l-lossy`.
Форматы и настройки есть в README архивов, контрольные суммы — в `SHA256SUMS`,
сравнение кадров — через вложенный `compare.py`. Это отдельный набор; числа
v3.2 выше получены на наших аналитических сценах, не на этом пакете.
